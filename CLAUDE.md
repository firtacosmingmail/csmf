# csmf.ro

Personal blog: Next.js web app + Supabase backend, pnpm/Turborepo monorepo.
Single admin user, public visitors read posts and leave moderated comments.
Work is tracked in Linear (team **FLE**, project **csmf.ro**), numbered
phases from repo setup to production deploy.

## Architecture

- **Database access goes through Supabase Edge Functions, not directly.**
  `apps/web` never queries Postgres/PostgREST itself for data. Every read or
  write to the six app tables goes through a REST API implemented as an Edge
  Function (Hono router) in `apps/supabase/functions/`. RLS is still the
  real enforcement layer — functions use a request-scoped client
  (`apps/supabase/functions/_shared/client.ts`) that forwards the caller's
  `Authorization` header, so a query runs with the *caller's* permissions,
  not the function's.
- **Auth is the one exception.** Supabase Auth (email/password) is called
  directly from `apps/web` via `@supabase/ssr` (`apps/web/lib/supabase/`,
  `apps/web/proxy.ts`) — it's a dedicated auth service, not "database
  access," so it isn't wrapped by the Edge Functions layer. The session JWT
  it produces is what gets attached to Edge Function calls.
- **Single-admin RLS model.** There's exactly one admin user, created by
  hand in the Supabase dashboard (no signup flow anywhere in the app). RLS
  policies treat *any* authenticated session as the admin: public reads are
  scoped to published posts / approved comments, `to authenticated` policies
  grant full access.

## Repo layout

```
apps/
  web/                    Next.js App Router site (the only public-facing app)
    app/                  Routes. app/admin/** is the protected admin area.
    lib/supabase/         @supabase/ssr clients (server/browser) + proxy.ts's session-refresh helper — auth only, no data access.
    proxy.ts              Next.js 16's middleware replacement (see Conventions). Protects /admin/*.

  supabase/               The Supabase CLI project root (config.toml lives here)
    migrations/           Historical migration log — timestamped, one per schema change, applied via `supabase db push`.
    seed.sql               Sample data for a fresh dev project.
    types/database.ts      Generated types (`pnpm --filter @csmf/supabase gen-types`). This package is types-only — see Conventions.
    functions/             Edge Functions (Deno + Hono). One directory per function.
      _shared/client.ts     Request-scoped Supabase client — every function that touches the DB should use this, forwarding the caller's Authorization header.
      _shared/http.ts        Shared pure helpers (Postgres-error → HTTP status, request-body field picking) — reusable, unit-testable logic every function's route handlers should build on.
    setup/                 Current-state SQL, NOT migration history — see below.
      storage/              Same convention, for Supabase Storage buckets.

  api-docs/               Swagger UI + the OpenAPI spec for the Edge Functions API — see Conventions.
```

## Conventions

### Commit messages reference the Linear ticket

When a commit implements (or is part of) a Linear ticket, include its ID
(e.g. `FLE-35`) in the commit message — in the subject line or the body.
Bug fixes / cleanup unrelated to a specific ticket don't need one.

### Coding

- TypeScript strict mode everywhere; `tsc --noEmit` must pass
  (`pnpm typecheck`), same for `pnpm lint`, `pnpm build`, and `pnpm test`,
  before calling work done.
- Tailwind v4, tokens defined in `apps/web/app/globals.css` (`@theme`
  block): `paper` / `paper-raised` / `ink` / `ink-muted` / `border` /
  `terracotta` (+ `-hover`) for color, `font-serif` (Newsreader) /
  `font-sans` (Source Sans 3) / `font-mono` (JetBrains Mono) for type. Use
  these tokens instead of raw Tailwind colors/fonts.
- Next.js 16 renamed the `middleware.ts` file convention to `proxy.ts`
  (exported function is also named `proxy`, not `middleware`) —
  `middleware.ts` still works but is deprecated and logs a warning. Use
  `proxy.ts`. This repo's version of Next.js may have other breaking
  changes vs. training data — `apps/web/AGENTS.md` (auto-regenerated by
  `next dev`/`next build`, don't hand-edit it) points at the bundled docs in
  `apps/web/node_modules/next/dist/docs/` for anything that looks off.
- New Edge Functions live in `apps/supabase/functions/<name>/`, use Hono for
  routing, and use `functions/_shared/client.ts` for any DB access (never
  the service role / a fixed anon client) so RLS applies as the caller.

### Unit tests

**Every Edge Function (API) and every piece of Next.js logic needs unit
tests.** For a route handler, that usually means extracting its non-I/O
logic into a plain, importable function (see `_shared/http.ts`) and testing
that, rather than the handler itself — same idea on the Next.js side for
anything more than trivial JSX (pure helpers in `lib/`, and client
components with real behavior, e.g. `post-form.test.tsx`'s slug auto-fill).
Write the test in the same change that adds or changes the logic, not as
follow-up.

- `apps/web`: Vitest + Testing Library (`vitest.config.mts`, jsdom
  environment). Tests live next to the code as `*.test.ts(x)`. Run with
  `pnpm --filter web test` (or `test:watch` while iterating).
- `apps/supabase`: Deno's built-in test runner. Tests live next to the code
  as `*.test.ts`. Run with `pnpm --filter @csmf/supabase test` (plain
  `deno test functions/` under the hood — add `--allow-*` flags to that
  script only if a future test genuinely needs a permission, e.g.
  `--allow-env`).
- `pnpm test` at the repo root runs both, via turbo.

### Swagger / OpenAPI docs (`apps/api-docs`)

`apps/api-docs/openapi.yaml` documents every Edge Function route.
**Whenever an API route is added, removed, or changed, update this spec in
the same change** — new/changed request or response shape, new endpoint,
new auth requirement, all of it. Run `pnpm --filter @csmf/api-docs dev` to
browse it locally (Swagger UI on `http://localhost:4400`).

### Database setup folder (`apps/supabase/setup`)

`apps/supabase/migrations/` is the historical log (how the schema got
here); `apps/supabase/setup/` is the current state (what it is now) — one
SQL file per table, each the full `create table` plus its indexes,
constraints, and RLS policies, numbered for dependency order. The point is
being able to stand up the database — schema, indexes, constraints, RLS,
everything — on any fresh Postgres/Supabase environment in one pass, without
replaying migration history. **Whenever a migration creates or alters a
table, create or update that table's file in `setup/` to match.**
`setup/storage/` is the same convention for Supabase Storage buckets — one
SQL file per bucket (bucket creation + its `storage.objects` policies).
